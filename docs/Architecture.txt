POKEPEDIA ARCHITECTURE

This document describes the checked-in runtime. See PROJECT_STATE.md for API details, gaps, and the recommended continuation order.

1. Runtime topology

Browser
  |
  | Next.js App Router pages and client components
  | Axios calls to NEXT_PUBLIC_API_URL
  v
NestJS API (`/api` prefix)
  |
  +-- PostgreSQL
  |     Drizzle ORM over node-postgres
  |     users, refresh tokens, Pokémon reference/form/join data
  |

  |     OTPs and email/reset verification flags

RabbitMQ, background workers, AI services, and deployment-specific infrastructure are not implemented.

2. Backend layers

- Bootstrap (`src/main.ts`): validation, CORS, global JWT guard, response interceptor, exception filter, `/api` prefix.
- Controllers: translate HTTP path/body/query parameters into service calls.
- Services: authentication rules, read queries, type calculations, and synchronization orchestration.
- Infrastructure: global DatabaseService and RedisService plus Mailjet/PokéAPI adapters.
- Drizzle schema: table definitions and relations under `src/database/schema`.
- Common layer: response metadata, public-route metadata, response envelopes, hashing, and OTP generation.

All routes are protected by default. `@Public()` is an explicit bypass. Public read routes include Pokémon and type data. The current public sync trigger is a known security gap.

3. Frontend layers

- `app/`: layouts and routes using the Next.js App Router.
- `components/`: auth workflows, type chart, navbar, and shadcn UI primitives.
- `services/`: backend endpoint adapters.
- `stores/`: Zustand state/actions for authentication and the type chart.
- `lib/api.ts`: Axios clients, bearer injection, refresh retry, and response-envelope unwrapping.
- `lib/validations/`: Zod form contracts.
- `types/`: shared client-side API/state shapes.

There is currently no server-side data-fetching layer and no active TanStack Query integration.

4. Main flows

Registration:

Next.js form -> send OTP -> Mailjet + Redis -> verify OTP -> Redis verification flag -> register -> bcrypt + PostgreSQL.

Authentication:

Login -> backend returns access and refresh tokens -> frontend stores access token in memory -> bearer token on authenticated Axios requests.

The reload/refresh/logout path is incomplete because the client assumes an HTTP-only refresh cookie while the backend requires a refresh token in the JSON request body.

Pokémon reads:

Client -> public Nest controller -> Drizzle query -> PostgreSQL -> standard response envelope -> Axios unwraps `data`.

Type chart:

Controller -> TypeService -> Redis lookup -> PostgreSQL relation exceptions -> expand neutral 1x cells -> cache for 24 hours. The frontend uses the matrix directly and calculates combined one/two-type defense in the browser.

Synchronization:

Public HTTP trigger -> in-process fire-and-forget SyncService -> sequential PokéAPI stages -> Drizzle upserts/deletes/inserts -> partial cache invalidation. The running flag is process-local and is not durable.

6. Architectural invariants

- Keep the `/api` prefix and response envelope synchronized with the Axios unwrapping layer.
- Make route access explicit; writes and operational actions must not accidentally be public.
- Keep species-level data separate from Pokémon form-level data.
- Preserve sync dependency order and make each stage idempotent.
- Generate and verify migrations whenever Drizzle schema changes.
- Keep access-token and refresh-token design consistent across browser and API.
- Do not introduce RabbitMQ, AI, or deployment services in docs until an implementation is checked in.
